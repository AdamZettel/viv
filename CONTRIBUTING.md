# Contributing to Viv

Thank you for helping. This file covers building, the checks a change must
pass, the bug ledger, the style guide and how to report a problem.

## Build

```sh
cargo build --release -p viv     # the compiler: target/release/viv
cargo test --workspace           # the kit and every language in the workspace
sh www/build-wasm.sh             # the browser compiler: www/public/viv/viv.wasm
```

You need Rust 1.77 or newer, a C compiler (clang or gcc), Node 24 for the site
and the wasm engine's tests, and Python 3.11 with NumPy 1.24.4 for the
comparison and translation checks (`lib/nprandom` reproduces that version's
random draws). The nightly checks also use PySCF 2.5.0 and Julia.

Code comments cite *the knotkit commitments* by section number (1.1, 2.5,
...): the kit's architectural charter, a separate document that is not part of
this repository. A change to one of those rules is discussed in an
issue first.

## The gate

The checks a change must pass are one fixed list in `tools/gate/gate.py`. Run
them through the gate rather than choosing a subset by hand:

```sh
tools/gate.sh quick              # the language checks: build, cargo test, the core three-engine set,
                                 # the ratchets, the bug ledger, the site's static checks
tools/gate.sh premerge           # what a merge runs: quick, the library engine-agreement set, the wasm
                                 # freshness checks, one small program per application family, and the
                                 # post-merge suites your branch's paths trigger (about 4 minutes warm,
                                 # 10 with a compiler change)
tools/gate.sh postmerge          # the application suites (SCF, HF, DFT, ports, posts), py2viv,
                                 # memcheck-quick, www-check, hub-golden, fast-identity
tools/gate.sh full               # premerge + postmerge
tools/gate.sh triggers           # which post-merge suites your branch's changes pull into premerge
tools/gate.sh quick --only <check>   # one check while you iterate
tools/gate.sh <tier> --list      # what a tier runs, and the command for each check
tools/gate.sh status             # the last runs
```

Run `tools/gate.sh quick` while you work and `tools/gate.sh premerge` before
you ask for a merge, and include its summary line in the pull request. A
branch that changes a library or application area runs that area's
post-merge suites in its premerge run: `lib/hf` or `scf` brings the SCF and
HF suites, `dft` the DFT check, `tools/py2viv` py2viv, `www` or `posts`
www-check, the C or wasm backend memcheck-quick, and a change to the gate
itself brings the whole post-merge tier (the table is `TRIGGERS` in
`tools/gate/gate.py`). The rest of the post-merge tier runs on `main` after
the merge. A failed check prints the tail of its log and the command that
reruns it. Fix the cause; do not drop the check or narrow what it covers.

Independent checks run at once within a budget (`GATE_CORES`, default the
core count less two; `GATE_MEM_GB`, default 10; one sanitizer-heavy check at
a time; timing checks alone). quick, premerge and full stop at the first
failure; `--keep-going` runs the rest, and `--serial` runs one check at a
time.

A check passes or fails on deterministic results only: the same inputs give
the same verdict on every run and every machine. Timings, network calls and
anything else that varies between runs are reported, never pass/fail. A
randomized check fixes its seed and prints it. A check that fails without a
code change is a bug in the check: quarantine it (take it out of the tier with
a ledger entry) and fix it before it comes back.

A new check goes into `CHECKS` in `tools/gate/gate.py` with a name, a command,
a tier and a weight (cores, memory, sanitizer-heavy), so every later run
includes it. An application suite goes in postmerge with a line in
`TRIGGERS` for its paths, and one small program of it in the smoke set.

## Merging

Branches reach `main` through `tools/merge.sh <branch>`, not `git merge`. It
merges with `--no-ff` in a separate worktree, runs the premerge tier on the
merged tree (with the suites the branch's paths trigger), and moves `main`
only if every check passed. Files in `www/src/data/` are regenerated by the
site's staging, so a conflict there takes `main`'s copy and the staging in
www-check rewrites it.

## Three engines

Every program must print the same bytes in the interpreter, as C and as wasm.
`tools/three-engines.sh <dir>` runs a directory of programs through all three
and fails on a failed test, a program without tests, or any difference in
output. A difference between engines is a bug in one of them, never a
tolerance to widen.

## The bug ledger

`bugs/ledger.jsonl` has one line per bug: its id, the date found, who or what
found it, the engines affected, whether the engines disagreed, and once fixed,
the commit, the root cause and a test.

- Add the bug when you find it, before you fix it.
- **Every fixed bug has a test**: `cargo:<package>/<target>::<function>` or
  `viv:<path>`. The gate's `bugs` check confirms every fixed bug's test exists
  and runs the `viv:` ones; cargo-test runs the cargo ones, so a regression
  fails the gate (`tools/gate.sh bugs --check --run` reruns them all).
- `tools/gate.sh bugs` prints the ledger's trend.

## Adding a feature

A new feature needs an entry in the catalog that `viv features` prints. That is
an entry in `lang/viv/features/<area>.txt` with an example, or a row in
`lang/viv/features/builtins.txt` for a builtin (the format is in
`lang/viv/features/README.md`). `cargo test -p viv --test features` runs every
example in all three engines and fails on a builtin with no row or an example
whose output changed.

A change to the language's behavior starts with a written proposal in the
issue or pull request: the problem, the options and what was measured.

## Style

- Viv code follows the house style below. `viv features --usage <files>`
  lists hand-written code that a feature replaces.
- Prose (documentation, comments the site shows, posts) is plain and specific:
  say what a thing does and give the number with its source. `npm run aispeak`
  in `www/` checks the site's text and the posts for
  phrasing the project avoids; `node www/scripts/aispeak.mjs <files>` checks
  named files. The deploy (`npm run build`, which Netlify runs) and the gate's
  www-static step run it as `npm run aispeak -- --strict`, so any hit fails them.
- A performance number cites the result file it comes from and says whether
  the run was provisional (timed under load) or final.

### The Viv house style

The goal is code a reader who knows the mathematics and some Python can follow
from top to bottom without the reference open, and that is never slower than
it has to be.

- **A call or a phrase.** Write a call when the def's name is the name the
  paper uses (`rmsnorm(X)`, `cholesky(A)`). Write a phrase when it names an
  operation the arguments or index arithmetic would hide
  (`take the last n elements of out`). Do not declare a phrase that stands for
  one call of a def with a clear name. A phrase is last on its line. Matrix
  notation stays notation: `Q = X @ Wq`.
- **Steps.** A step of one statement that fits in 100 columns is one line
  (`step mlp_norm: N2 = rmsnorm(X1)`); anything longer is braced. Group by the
  paper's operations, not by statements. `tools/steps/one_line.py FILE` lists
  braced steps that fit on one line, and `--fix` rewrites them.
- **Names.** `snake_case` for defs, variables and parameters; `CamelCase` for
  records, enums, their variants and constructor defs; `UPPER_CASE` for
  top-level constants. Mathematical names as the paper writes them (`X`, `Wq`,
  `D`). One letter is fine for a loop index or a name the paper uses; a
  quantity a reader has to look up gets a word. No suffixes that encode a type
  (`_arr`) or a version (`_v2`): a second version is a registry member whose
  name says how it differs (`jk_packed`, `jk_dense`).
- **A comprehension or a loop.** A comprehension when the loop builds one
  value and does nothing else. A loop when the body writes into an array in
  place, contains a step, accumulates more than one value, or stops early.
  Never `x = []` followed by `x = append(x, ...)` when the count is known, and
  never a one-cell array as an accumulator.
- **Step text.** A step's id names the operation (`scores`, `mask`). It gets a
  text when the id does not say what the paper's sentence says, or when the
  step does something a reader would not expect (a guard, a fallback, a
  reordering for speed). Longer explanations go in the `.intent` file.
- **Def length.** Under 40 code lines, or divided into steps that each read as
  one operation. A def does one thing a caller would name. Generated defs are
  exempt and marked as generated.
- **Production and verification.** Speed work sits beside the readable
  algorithm, never in place of it: a def made fast in a way that hides the
  algorithm (packed storage, symmetry folding, a different summation order) is
  the production member of a registry, and the plain statement of the same
  computation is its check member, held equal by a test that states its
  tolerance. lib/hf's `jk_packed` and `jk_dense` are the model.
- **Imports.** At the top, one module per line. `from nn import a, b` for the
  few names a file calls often; `import cas` and `cas.diff(...)` for a module
  with many names. No unused imports.
- **Layout.** 100 columns. A record literal or a call that does not fit puts
  one field or argument per line, with a trailing comma. A def body is never on
  the def's line, `else` starts its own line, and there is one `for` and one
  `}` per line (`npm run vivfmt` in `www/`). No magic sizes: `viv lint`
  reports integer literals used as sizes and loop bounds; name them or take
  them from `len` or `shape`. One statement per line.
- **Named options.** A builtin's options and a def's defaulted parameters are
  keywords at every call (`sum(X, axis=-1)`), and so is a boolean argument
  (`fit(X, centered=true)`).
- **Loop-invariant work.** A gather or slice copy whose index does not change
  inside a loop is computed before the loop.

## Reporting a bug or friction

Use the issue templates:

- **Bug report**: the smallest program that shows it, what you expected, what
  happened, and which engines are affected (interpreter, C, wasm, fast mode,
  the browser).
- **Friction report**: something that works but is awkward to write. Give the
  Python (or other language) you would have written, the Viv you had to write,
  and one code from the friction rubric (`no-set`, `no-tuple-key`,
  `no-map-literal`, `map-of-collections`, `double-sort`, `float-as-int`,
  `manual-string-building`, `no-generator`, `no-exception`, `flat-record`,
  `no-ragged`, `index-arithmetic`, `extra-copy`, `missing-builtin`,
  `manual-numeric-type`, `no-closure-state`, `loop-not-comprehension`,
  `syntax-gap`, or `other` with a short note).
- **Feature request**: the problem it solves and a small example of the code
  you want to write.
