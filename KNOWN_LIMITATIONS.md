# Known limitations

Viv 0.0.1 is a preview. This file lists what does not work yet, from the records the repository keeps. It is generated by `tools/release/known_limitations.py`; edit the sources, not this file.

## Platforms

- **macOS and Linux** build the compiler and the C it writes, with Clang or GCC. Only macOS on arm64 has run the exported programs' checks so far.
- **Windows**: MinGW-w64 GCC and Clang should build the generated C and the exported programs, but this is untested. MSVC is unsupported: it lacks C99 `_Complex`.
- **Python**: a module written by `viv export` needs Python 3.9 or newer and NumPy; it refuses to import on an older Python.

## Language gaps found by the Rosetta Code study

From the Rosetta Code study's records: 100 Rosetta Code tasks written in Python and in Viv. A *missing* feature is one a task needed and Viv lacks; *friction* is something Viv can do only in a longer or less direct way. Ranked by the number of tasks affected.

### Missing

| feature | tasks | note |
|---|---|---|
| tuples | 3: run_length_encoding, dijkstra_s_algorithm, knapsack_problem_0_1 | no tuple values: a list of (character, count) pairs is an array of records, and a tuple key or tuple comparison is spelled out by hand. |
| arbitrary-precision decimals | 2: nth_root, pi | No decimal type; a computation asked for to N > 16 digits runs in doubles. |
| command-line arguments | 2: command_line_arguments, a_b | no argv; `--set NAME=value` replaces a top-level constant but takes numbers only, so no string can come from the command line. |
| map values that are collections | 2: topological_sort, dijkstra_s_algorithm | a map holds numbers or strings only, so a map from a name to a set or list of names (an adjacency list) is a string of names joined by spaces, or a walk over an edge list. |
| memoizing a def that returns a list (lru_cache) | 2: proper_divisors, amicable_pairs | No lru_cache, and a map holds numbers or strings, not arrays, so a list-valued function cannot be memoized in a map. |
| arbitrary-precision rationals | 1: numerical_integration | Python's fractions.Fraction has no Viv counterpart; lib/cas/rational is exact only while numerators fit in doubles. |
| complex power | 1: arithmetic_complex | `^` refuses a complex operand; the pair writes CPython's c_pow by hand. |
| copysign | 1: arithmetic_complex | No copysign/signbit builtin to tell -0.0 from +0.0. |
| decorators | 1: catalan_numbers | No @decorator; memoization is a map per def, written into the def. |
| exact rationals (fractions) | 1: gaussian_elimination | no Fraction type: lib/cas/rational holds p/q as two doubles (exact below 2^53), so a matrix of fractions is two matrices and every operation is a call returning two numbers. |
| generators | 1: prime_decomposition | No yield; an infinite prime stream becomes explicit state (a map and an [Int] of counters) advanced by a def. |
| math.fsum | 1: averages_arithmetic_mean | No exactly rounded sum builtin; the pair writes Shewchuk's partials by hand. |
| math.hypot | 1: monte_carlo_methods | no hypot builtin; defined as sqrt(x*x + y*y) (without hypot's overflow care). |
| ragged lists (a list of lists of different lengths) | 1: pascal_s_triangle | An array of arrays must be a rectangular matrix; Pascal rows cannot be collected in one value. |
| recursive records | 1: tree_traversal | a record cannot hold optional records of its own type (a tree node with left/right children), so a tree is index arrays with a NONE sentinel. |
| unique() of numbers | 1: n_queens_problem | `unique` takes strings only (np.unique is lib/algo, not built), so `len(set(...))` of numbers is a marking array. |

| function values from an array | 1: numerical_integration | `[f, g]` holds function values but `fs[i]` can only be called with `apply(fs[i], ...)`; it cannot be passed as a function argument (`integrate(fs[i], ...)` is refused), so a loop over a tuple of functions is written o... |
| growable Int arrays | 1: sieve_of_eratosthenes | `append` takes a real array only: an [Int] cannot grow (`p = int_zeros(0); p = append(p, k)` is refused), and an Int cannot be appended to a number array without float(); the sieve keeps its primes as numbers. |
| Int and Num arguments do not mix | 1: numerical_integration | An `n: Int` parameter refuses a number literal constant and an Int refuses a Num parameter; a size used both in arithmetic with doubles and in an f-string is simplest left a Num and printed with `:d`. |
| Int map keys | 1: prime_decomposition | `m[k]` with k: Int is refused ('a map key must be a number or a string'); keys are written float(k). |
| Int where a number is expected | 1: sorting_algorithms_quicksort | an Int does not pass where a number is expected (`append(xs, i)`, `chr(97 + i)`): each needs float(i). |

| min/max of three or more arguments | 1: levenshtein_distance | `min(a, b, c)` is refused (two arguments); written min(min(a, b), c) or min([a, b, c]). |
| nested format specs | 1: tree_traversal | `f"{name:>{w}}"` (a width from a variable) is not accepted, and fmt's spec must be a literal; rjust(name, w) does it. |
| print of a large whole number | 1: prime_decomposition | print(1059490.0) writes 1.05949e+06 (six significant digits); a count kept as a number prints exactly only through {x:d} or an Int. |
| printing an array in an f-string | 1: amicable_pairs | print(xs) writes [1, 2] but f"{xs}" writes [1.0, 2.0]; a list of integers in a sentence needs a join of {x:d} fields. |
| sorted() of numbers | 1: loops_foreach | `sorted` takes a list of strings or a string; a number array needs `s = copy(xs)` then `sort(s)` on its own line. |
| trailing comma in a list literal | 1: dijkstra_s_algorithm | `[a,\n b,\n]` is a parse error; Python and the task's code allow the trailing comma. |
| unique() of numbers | 1: set | `unique` takes a string or a list of strings; the distinct numbers of an array (np.unique) wait on lib/algo, so a set of numbers is deduplicated by hand. |

## Benchmark cells Viv could not run

From `study/benchmarks/limitations.json`, written from the benchmark study's last pass. Some reasons may predate later work (for example, Viv now has `Int` and a `clock()` builtin); the next benchmark pass updates them.

| cell | why |
|---|---|
| Benchmarks Game mandelbrot, all Viv engines | The output is a binary PBM (bytes 0-255). Viv writes UTF-8 text only (`print`, `write_text`), so no Viv program can produce the benchmark's bytes. |
| Benchmarks Game binary-trees, all Viv engines | The benchmark allocates recursive tree nodes. Viv forbids recursive record types and has no pointers or references; a tree kept in a preallocated array is a custom memory pool, which the Benchmarks Game rules for this benchmark do not accept. |
| Benchmarks Game pidigits, all Viv engines | Needs arbitrary-precision integers. Viv's only number is a 64-bit float. |
| Benchmarks Game, Numba column | The Benchmarks Game has no Numba programs; none were written. |
| numpy-benchmarks, Julia column | No published Julia version of these kernels was found (searched the suite's repository and the web); none was written for this study. |
| numpy-benchmarks, 12 kernels, all Viv engines | Refused by py2viv (strict), each at a construct inside the kernel: `np.bitwise_and` (check_mask), the sum of a complex array (cma_pt), `.var(ddof=)` (cronbach), `dtype=np.float32` (grayscott), a default argument that is a function (local_maxima), `np.average` (lstsqr), `dtype=E.dtype` (make_decision), real array times a complex number (mandelbrot), a real value added to a complex array (normalize_complex_arr), `np.tile` (periodic_dist), `np.repeat` (repeating), a row view that the code writes into (wave). |
| numpy-benchmarks, Numba "unsupported" | Numba's nopython mode rejects the kernel as the suite's harness decorates it (np-bench reports these as "unsupported" too): check_mask, cronbach, evolve, grouping, local_maxima, make_decision, mandelbrot, periodic_dist. |
